## What this round shipped

End-to-end "every pipeline_complete records a privacy-redacted summary
that operators can later inspect via authenticated route" loop in
4 sub-slices.

### Sub-slice S4-a — `runMemory.js` runtime module
- New `src/runtime/runMemory.js` (~370 LOC for module body, +160 for derive helper)
- Frozen vocabulary: `SCHEMA = "harness-run-memory/v1"`, `AUDIT_VERBS = {RECORDED, ACCESSED}`, `FIELD_LIMITS` per-field caps (256/2K/4K/512/1K)
- 6 privacy guards baked in (per plan §S §S-SMART-4 v2):
  1. **TTL-friendly** — records live in evidenceLedger as `run_memory_recorded` audit rows; existing TTL machinery covers them
  2. **Opt-out** — `ORCHESTRATOR_RUN_MEMORY_DISABLE=1/true/yes` → `recordRunMemory` returns `{recorded:false, reason:"disabled_by_env"}` immediately
  3. **Per-field max length** — overflow → truncate + ellipsis + `truncated:true` flag
  4. **NO raw text persistence** — diff/patch raw bodies NEVER stored; `sourceHash` (sha256) lets a forensic auditor verify content-match without the bytes being on disk
  5. **Public-sector redaction** — every text field passes through `piiScanner.scanForPii` under `publicSector` posture; PII replaced with `[REDACTED:<type>]` + `redacted:true` flag + `redactedTypes` list
  6. **Public-sector route auth+audit** — getRunMemory itself is pure; HTTP route layer (S4-b) enforces loopback + x-harness-token + emits `run_memory_accessed` audit
- API: `buildRunMemoryRecord(runId, inputs, opts)` (pure builder, returns frozen record), `recordRunMemory(opts)` (persistence wrapper, defensive against ledger throws), `getRunMemory(runId, ledger)` (latest record, defensive against read throws), `computeSourceHash(content)` (canonical sha256), `deriveFromPipelineSnapshot(snapshot)` (S4-c: project pipeline_complete event into runMemory inputs)
- 46 unit tests for the core module + 27 unit tests for `deriveFromPipelineSnapshot` = 73 unit tests total

### Sub-slice S4-b — `GET /api/runs/:runId/memory` route
- New `src/routes/runMemoryRoutes.js` (single endpoint)
- Auth contract: loopback only (covered by global x-harness-token middleware in server.js)
- Audit policy: `run_memory_accessed` fires on found AND not-found reads (operator tracking sees "tried to read run X at time Y" even when nothing was there); does NOT fire on 400 (operator UI bug)
- Implementation note: route probes `ledger.read` directly with own try/catch instead of trusting `runMemory.getRunMemory`'s defensive swallow. Reason: `getRunMemory` returns null on ANY ledger error (callers who want unified "no record" signal), but route layer needs to distinguish "ledger broken" (503) from "no record yet" (404)
- 13 integration tests covering: 200 + record / 404 with audit / 400 NO audit / 503 with audit / missing dep stub / throwing auditFn / public-sector pre-redacted on the wire / latest-wins on multi-record / truncated metadata in audit / opt-out 404
- `server.js` mounts at `/api` with `auditFn: evidenceLedger.append.bind(evidenceLedger)`

### Sub-slice S4-c — Pipeline-executor `onRunComplete` hook + server wiring
- `executor/pipeline-executor.js` constructor accepts new optional `onRunComplete(runId, snapshot)` callback
- `_complete()` invokes it AFTER `broadcast(pipeline_complete)` with the SAME snapshot — UI + memory guaranteed consistent
- Wrapped in `try/catch` — recorder failure (ledger I/O, redactor throw, opt-out env, anything) NEVER breaks the `_complete` path
- `server.js` `PipelineOrchestrator.createExecutor` passes `onRunComplete: (runId, snapshot) => runMemory.recordRunMemory({runId, inputs: runMemory.deriveFromPipelineSnapshot(snapshot), ledger: evidenceLedger, deploymentProfile: _deploymentProfile})`
- 10 unit tests for callback firing semantics + ordering + defensive throw handling + null-callback regression
- Lazy `require` inside the callback (no extra boot cost when pipeline never completes; matches existing late-require pattern elsewhere in server.js)

## End-to-end loop verification

Public-sector + standard scenario:

1. PipelineExecutor runs to completion (any reason)
2. `_complete(reason)` fires
3. `broadcast({type: "pipeline_complete", data: snapshot})` — UI sees it
4. `onRunComplete(runId, snapshot)` fires
5. Inside the callback: `runMemory.recordRunMemory({runId, inputs: runMemory.deriveFromPipelineSnapshot(snapshot), ledger: evidenceLedger, deploymentProfile: {publicSector: true}})`
6. Inside `recordRunMemory`:
   - `_isOptOut(env)` → false (ORCHESTRATOR_RUN_MEMORY_DISABLE not set)
   - `buildRunMemoryRecord(runId, inputs, {deploymentProfile: {publicSector:true}})`
     - Each text field truncated to FIELD_LIMITS cap → truncated:true if any
     - Each text field passed to `_safeRedactString(text, dp)` → if PII, replaced with `[REDACTED:<type>]` + redactedTypes collected
     - Returned frozen record with `schema: "harness-run-memory/v1"`, `runId`, `recordedAt`, `truncated`, `redacted`, `redactedTypes`, `sourceHash`, `fields`
   - `ledger.append(runId, {type: "run_memory_recorded", data: record})` — chain hash advances
7. Operator later: `GET /api/runs/<runId>/memory`
   - `_validateRunId` passes
   - `ledger.read(runId)` returns entries
   - Walk backwards for latest `run_memory_recorded` → memory found
   - `_safeAudit(auditFn, "run_memory_accessed", {runId, found:true, recordedAt, truncated, redacted})`
   - 200 + `{ok, runId, memory, recordedAt}` — already-redacted record on the wire

Verified end-to-end via:
> `deriveFromPipelineSnapshot + recordRunMemory: round-trip on realistic snapshot` (runMemory.derive.test.js)
> `S4-b routes: public-sector recorded record arrives ALREADY redacted` (run-memory-routes.test.js)
> Pipeline-executor + recordRunMemory + ledger persist + route read: full chain.

## Decisions worth re-reading later

1. **Privacy-by-design baked into the runtime, not the route**: `recordRunMemory` does the redact at WRITE time. The route is a pure read. This means even if a future bug bypasses the route auth check, the persisted record is already redacted — there's no plaintext PII in the ledger to leak. SMART-2 invariants applied at a different layer.

2. **`computeSourceHash` is the audit-trail substitute for raw diff**: Operators / forensic auditors want to verify "yes, run X touched these exact bytes" without the bytes being on disk. The sha256 hex digest serves both purposes — auditor re-hashes the source files to verify, and the hash itself reveals nothing about the content.

3. **Audit-verb shape carries the WHOLE record**: `ledger.append(runId, {type:"run_memory_recorded", data: <full record>})`. Reasoning: there's no separate persistence layer for run memory. The ledger entry IS the memory. This means TTL cleanup automatically covers it, and chain verification (R1-c HMAC) covers tampering.

4. **`deriveFromPipelineSnapshot` is intentionally lossy**: A full pipeline transcript can be 100 KB+. The derived inputs cap at ~8 KB before redaction. This means run memory is a SUMMARY suitable for "did the run go OK?" / "what severity were the findings?" questions, not "show me Codex's exact response on phase 2".

5. **`onRunComplete` callback at PipelineExecutor not Orchestrator**: The orchestrator could have intercepted `pipeline_complete` events from the broadcast stream, but a direct callback gives synchronous ordering ("memory recorded BEFORE this.active = null") and is easier to test. Plan §S §S-SMART-4 trade-off accepted.

6. **Defensive try/catch at every layer**: `_complete` catches `onRunComplete` throw; `recordRunMemory` catches `ledger.append` throw; `_safeRedactString` catches `scanForPii` throw; route catches `auditFn` throw. Memory is observability + lessons-learned, NEVER critical-path. Five layers of catch ensure a recorder failure can't cascade into a broken pipeline.

7. **`_safeRedactString` fail-loud on scanner throw under public-sector**: When `scanForPii` itself throws (regex compile error, etc.), the function returns `[REDACTED:scanner_failure]` instead of letting plaintext through. Conservative choice — matches `gatePiiBlock`'s scanner-failure-fail-closed precedent from SMART-2.

8. **Approvals are counts ONLY (not names / decider IDs / reasons)**: The decider IDs / reasons could carry PII or organizational signals. Storing only counts means "3 grants, 1 deny, 0 timeouts" — enough for trend analysis, nothing for re-identifying the decider.

9. **`piiDetected.types` capped at 16 entries**: A finding with hundreds of PII type tags would balloon storage. 16 is enough for "many distinct types found" without being unbounded.

10. **Lazy require inside server.js callback**: `require("./src/runtime/runMemory")` lives inside the `onRunComplete` lambda. No extra boot cost when no pipeline ever completes (e.g., harness up but never used). Matches the late-require pattern server.js already uses for `createReviewSessionRoutes` etc.

## What's deferred / out of scope

- **UI panel for run memory**: A future "기억" tab in the run-viewer panel would render the JSON record as a friendly summary (severity badges, redaction warnings, source-hash verifier link). Out of scope for SMART-4; module + route ready when UI lands.
- **Operator-curated `nextTimeWatchOuts`**: The derive helper extracts from `verification.results`, but a true "lessons learned" field would need an operator-input route (`POST /api/runs/:runId/memory/notes`?). Plan §S §S-SMART-4 leaves this as a future enhancement.
- **`sourceContent` from pipeline-executor**: The derive helper always returns null because pipeline-executor doesn't carry diff blobs through state by default. A future `state.lastDiff` channel could supply this. Module ready.
- **Cross-run memory listing**: `GET /api/runs/memory` (list all run memories) intentionally NOT shipped — risks listing PII across operator sessions in public-sector. If needed, would require careful scoping (operator-id filter, per-template grouping).
- **Manual delete endpoint**: TTL is the cleanup mechanism. Manual delete (`DELETE /api/runs/:runId/memory`) would need its own audit verb + posture check. Out of scope.
- **`run_memory_record_failed` broadcast event**: When `onRunComplete` swallows a recorder throw, the operator dashboard has no signal. A future enhancement could broadcast this event for operator visibility, but for SMART-4 we keep `pipeline_complete` shape unchanged (regression-safe).
