**Test strategy**: Regex-match key CSS selectors in the stylesheet
file. We're not testing pixel-perfect output (that's a visual diff
tool's job); we ARE testing that the key selectors required by the
panels' data-attribute hooks exist. If a future edit deletes
`.rec-row[data-severity="critical"]` (or similar), the test fails
fast — the panels' data attributes would lose their styling cue
silently otherwise.

## 6 decisions worth re-reading

1. **Selector-presence tests, not pixel-diff** — the alternative
   was Puppeteer/Playwright screenshot comparison, but that adds a
   new dev dependency, a CI step, and a maintenance burden (every
   browser update can shift sub-pixel rendering). Selector-presence
   tests catch the same class of regression (someone deletes a key
   rule) without the infrastructure cost.
2. **Shared chassis + per-panel specifics** — instead of copy-
   pasting border+radius+padding across `.nac-card / .rec-card /
   .pic-card`, the chassis is a single grouped selector. Future
   token rollouts hit one rule, not three.
3. **Data-attribute hooks, not class-toggle for severity** — the
   panels already set `[data-severity="critical"]` etc. CSS reads
   those. The alternative was JS-toggled classes (`is-critical`,
   etc.) but that means panels have to know the styling vocabulary.
   Data attributes keep the contract narrow: panel sets the data,
   CSS reads it.
4. **Green tint for `system-ready`, not info-blue** — the
   SMART-1-BASELINE-a rule has severity `info` (matching the
   existing classification) but the visual treatment leans into
   "all clear" (green) rather than "informational" (blue). Severity
   stays in the engine; visual semantics stay in CSS. The green
   only fires when the rec ID matches — generic info severity stays
   blue.
5. **Mobile breakpoint at 720px, not 600px** — 720px is the width
   below which the 3-column rec-row visibly squeezes the CTAs (per
   manual measurement on the live dashboard). 600px would also
   work but rec-row-with-CTAs starts feeling cramped at ~720.
6. **Reveal-on-hover dismiss button** — the dismiss button is
   visually low-contrast (opacity 0.5) until the row is hovered or
   the dismiss is focused. Always-visible dismiss buttons compete
   with the primary CTA for attention; revealing them on hover
   keeps the primary action front-and-center while remaining
   accessible (hover + focus-visible both reveal).

## What's deferred / out of scope

Foundation is shipped; these are follow-up slices:

- **Light-mode theme** — all CSS-1 rules use design tokens, so a
  future light-mode would just need a `:root[data-theme="light"]`
  override at the token level. Not in scope here.
- **High-contrast mode** — same pattern; would override tokens
  rather than per-panel rules.
- **Pixel-diff testing** — Playwright/Puppeteer screenshot
  comparison against a golden baseline. Selector-presence tests
  catch structural drift; they don't catch CSS computed-value
  regressions (e.g., someone changes `padding: 14px` to `padding:
  4px` — selectors still match but layout breaks). Worth doing
  if visual regressions become a real problem.
- **Welcome-overlay (UI-H8) styling** — the welcome-overlay panel
  (UI-H8) has its own `.wo-*` selectors that this round didn't
  touch. The overlay is currently styled (it has CSS) but a future
  round could harmonize it with the CSS-1 design language.
- **Approval-card (R3-e + UX-2) styling polish** — the
  approval-card has CSS but could benefit from CSS-1-style severity
  tones (write-tool approvals are higher-stakes than read-tool).
- **CSS-2 round** — the harness has many other surfaces
  (`.bd-tabs`, `.dac-*`, `.rt-*`, etc.) that have CSS but might
  benefit from a similar systematic review. CSS-1 covered the
  three most-visible operator-facing banner cards; CSS-2 could
  look at workflow surfaces.
