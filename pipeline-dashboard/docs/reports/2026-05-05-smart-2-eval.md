### Sub-slice S2-a — `policyGates.js` module
- New `src/policy/policyGates.js` (~430 LOC)
- Frozen vocabulary:
  - `SCHEMA = "harness-policy-gate/v1"`
  - `GATE_MODES = {HARD: "hard", WARN: "warn"}`
  - `GATE_NAMES = {PII_BLOCK, RELEASE_SIGNED, EVIDENCE_EXPORT_READY, COMPLETION_ALLOWED}`
  - `GATE_REASONS = {PII_DETECTED, PII_SCANNER_FAILED, RELEASE_UNSIGNED, EVIDENCE_NOT_READY, COMPLETION_PENDING, NOT_APPLICABLE}`
  - `AUDIT_VERBS = {BLOCKED: "policy_gate_blocked", WARN: "policy_gate_warn"}`
- `resolveGateMode(env)`: ORCHESTRATOR_HARD_GATES=1/true/hard → HARD; default → WARN. Public-sector posture does **not** auto-imply hard mode; operators tune posture and strictness as separate switches (graduated rollout).
- 4 gate functions, each returns frozen verdict `{ok, blocked, mode, gate, reason, message, audit:{verb,data}|null}`:
  | Gate | Decision matrix |
  |---|---|
  | `gatePiiBlock` | public-sector + hard + PII detected → BLOCK; public-sector + warn + PII → ok+warn audit; standard + any + PII → ok+warn audit (observability). Scanner-throw fail-closed under public-sector+hard. Circular args → ok+warn audit (unserializable, never blocks). |
  | `gateReleaseSigned` | public-sector + !manifestSigned + hard → BLOCK; public-sector + warn → ok+warn; standard → NOT_APPLICABLE. Missing `manifestSigned` arg under public-sector+hard treats as unsigned. |
  | `gateEvidenceExportReady` | public-sector + !ctx.auditExportReady + hard → BLOCK; warn → ok+warn; null context + public-sector + hard → fail-closed. |
  | `gateCompletionAllowed` | post-state soft gate; needsHumanDecision + public-sector + hard → BLOCK; standard NEVER hard-blocks (warn only). Counts + booleans land in audit data. |
- `runGateChain(gates)` short-circuits at first blocked verdict; gate that throws → blocked verdict with `pii_scanner_failed` reason + `policy_gate_blocked` audit. Malformed entries (null / no .evaluate) silently skipped.
- 48 unit tests: SCHEMA + 4 frozen-vocabulary checks; resolveGateMode 8 variants; gatePiiBlock 11 scenarios (clean/empty/PII×3 modes/scanner-throw×2/object args/circular/sample landing/real scanner integration); gateReleaseSigned 5; gateEvidenceExportReady 5; gateCompletionAllowed 5; verdict immutability 2; runGateChain 6 (empty/all-pass/short-circuit/throw/warn-continues/malformed-skipped).

## End-to-end loop verification

Public-sector + hard scenario:

1. Operator UI sends `POST /api/review-sessions/<id>/send-codex {instruction: "review jane.doe@example.com profile"}`
2. `_resolvePresetId` (S3-c): `null` → no preset error
3. `_runPreStateGates`: scans `body.instruction` via `piiScanner.scanForPii`
4. Scanner returns `{hasPii: true, findings: [{type: "email", count: 1, samples: ["ja**@ex******.com"]}]}`
5. `gatePiiBlock` returns frozen verdict: `{ok: false, blocked: true, mode: "hard", gate: "pii_block", reason: "pii_detected", message: "Public-sector posture + hard gate refuses dispatch: PII detected (email).", audit: {verb: "policy_gate_blocked", data: {gate, source, publicSector: true, findingCount: 1, findingTypes: ["email"], samples: {email: ["ja**@ex******.com"]}}}}`
6. `auditFn(verb, data)` emits `policy_gate_blocked` to evidenceLedger (chain hash advances by 1)
7. `_emitGateBlockedResponse` returns HTTP 409
8. `manager.sendCodex` is NEVER called → state stays `created`
9. `dispatcher.dispatchCodex` is NEVER called → no `review_session_dispatch_failed` audit
10. `codexRunner.exec` is NEVER called → no Codex spawn

State machine + approval queue + runRegistry: untouched. Audit chain: exactly +1 entry (`policy_gate_blocked`).

## Cap movement decision

Plan §S §S-score-trajectory predicted "+SMART-2 (hard gates) | **120/126** (Safety cap +1 보수)". The current scorecard is already at 120/126 (UI-P12 a11y delivered the +1 mid-stream into Public-sector cap 5/5).

**Decision: Stay at 120/126.**

Rationale:
1. Current Safety cap (cap 14) maps to: PII detection / signed manifest / sealed audit export / loopback gate / token model / posture refusal. SMART-2 adds **enforcement layering** on top — not a new safety property, but a stronger decision boundary.
2. The qualitative shift ("PII pre-state hard refuse + state-immutability invariant + single-audit") is genuinely new behavior, but its value only fully materializes when:
   - Operators flip `ORCHESTRATOR_HARD_GATES=1` in actual public-sector deployments
   - Ledger samples show `policy_gate_blocked` entries firing on real-world traffic
   - The gate chain is wired into the hook-router write-tool flow (S2-future)
3. Plan §S Risk register flagged "정상 작업 막힘" (workflow-blocking false positives) as the primary mitigation reason for warn-default. Moving cap before live-deployment evidence would be premature.
4. SMART-4 (Redacted Run Memory) + SMART-5 (Institutional Policy Packs) are still ahead. Both will exercise the gate chain. Cap movement is more defensible after one of those rounds adds real enforcement evidence.

The trajectory entry in scorecard.md records "SMART-2 closed at 120/126 — gates ready, hard mode opt-in" rather than a cap bump. This matches plan §S §S-SMART-2 risks → "warn mode default + UI toast" being the safe-rollout choice.

## Decisions worth re-reading later

1. **Warn mode default**: Hard gates are opt-in (`ORCHESTRATOR_HARD_GATES=1`). Existing public-sector deployments stay at warn until operator flips. Avoids breaking workflows on day one of SMART-2 deploy.

2. **Public-sector posture does not auto-imply hard mode**: The two switches are independent (ORCHESTRATOR_DEPLOYMENT_PROFILE=public-sector AND ORCHESTRATOR_HARD_GATES=1). Lets operators run public-sector posture with warn-only gates while observing audit volume.

3. **State-immutability invariant**: Gates fire BEFORE `manager.transition()`. If a gate is added AFTER state mutation, that's a bug. Anchored by integration test that asserts `manager.get(id).state === "created"` after a HARD block on `send-codex`. Plan §S risk: "gate가 audit 발사 후 dispatcher가 dup 발사" — addressed by gate-then-state ordering + integration test.

4. **Audit single-emit invariant**: When a hard gate blocks, the route returns 409 immediately. `dispatcher.dispatchX` is never called → no `review_session_dispatch_failed` cascade. Test asserts `audit.events.filter(e => e.verb === "review_session_dispatch_failed").length === 0` after a hard block.

5. **Defensive try/catch on auditFn**: An `auditFn` that throws (e.g., evidence ledger HMAC verification failure mid-run) must NOT break the route. Test: `auditFn = () => { throw new Error("audit DB down") }` + warn-mode + PII → route still 200.

6. **Preset validation (S3-c) before policy gate**: A typo'd preset returns 400 BEFORE the policy gate runs. This avoids running the gate (which scans text + emits audit) on a request that's going to be rejected anyway. Sequencing: route layer = `presetValidate → policyGate → managerTransition → dispatcherKick`.

7. **`gatePiiBlock` in standard mode is observability-only**: Standard posture sees `policy_gate_warn` audits but NEVER hard blocks. This is intentional — the GOV-PII-0 runner-side enforcement is the safety net for standard mode (operator chose not to opt into strict gates; the runner gate still refuses provider dispatch on actual PII).

8. **`gateCompletionAllowed` is post-state soft gate**: The other 3 gates fire pre-state (refuse before mutation). Completion is different — by the time completion is evaluated, mutation already happened. The gate's job is to flag premature completion (`needsHumanDecision === true`) so the operator dashboard can render a warning. Public-sector + hard CAN block phase completion; standard NEVER hard-blocks completion. Not wired in this round (no pipeline-executor integration); module is ready when a future round wires it.

9. **`gateReleaseSigned` is duplicative with E3-F1 launcher gate**: That's intentional. E3-F1 catches at install time; `gateReleaseSigned` re-checks at runtime for cases where a runner uploads/loads an unsigned manifest mid-process. Defense in depth.

10. **Module separation from `publicSectorPolicy.js`**: `publicSectorPolicy.js` keeps its scope (config-time validation + spawn-time asserts that throw). `policyGates.js` is the verdict-returning consolidator. Two modules avoid API contract bleed; tests + dashboards lock the vocabulary at frozen module load.

## What's deferred / out of scope

- **Hook-router wiring**: `executor/hook-router.js._dispatchSanitized` already has GOV-PII-0 (`piiGate.evaluatePiiBlock` from runner perspective). Wrapping it in the new `policy_gate_*` audit vocabulary at the dispatcher layer is value-add, but the route-layer wiring is the primary pre-state seam for review-session flows. Hook-router gate-chain wiring can be a follow-up SMART-2.5 round.
- **Pipeline-executor post-state wiring**: `gateCompletionAllowed` exists but isn't wired into `executor/pipeline-executor.js` phase completion. Pipeline-executor's phase-complete logic is distributed across multiple methods (recordPhaseComplete, advancePhase, etc.); a focused S2-d round would wire it. Module is ready.
- **`gateReleaseSigned` runtime wiring**: E3-F1 covers the launcher gate; the runtime version is only valuable if a runner ever uploads/loads a manifest mid-process. Wire when that scenario emerges.
- **`gateEvidenceExportReady` wiring**: No "release-ready" endpoint currently exists in the harness — this gate is forward-compatible for a future operator-export route. Module ready, no consumer yet.
- **Live deployment evidence**: Cap movement is contingent on actual operator deployment with `ORCHESTRATOR_HARD_GATES=1` + audit-chain samples. Future LV round (`scripts/live-verify-policy-gates.js`?) can produce that evidence.
- **`scripts/live-verify-policy-gates.js`**: Would exercise the full chain on a real binary similar to LV-1's review-relay smoke. Not required for SMART-2 closure.
