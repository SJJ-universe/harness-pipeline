**Schema**: `harness-decision-context/v1`
```js
{
  schema, timestamp,
  booleans: { 8 frozen flags },
  counts:   { 5 numeric counters },
  posture:  { mode + 5 flag mirrors },
  sources:  { per-adapter status: "ok" | "absent" | { errored, message } },
}
```

**8 documented booleans**:
1. `hasPii` — opt-input flag (piiScanner is stateless)
2. `approvalPending` — approvalManager.list() length > 0
3. `codexReviewMissing` — any awaiting_critique session
4. `auditExportReady` — evidenceLedger has entries
5. `publicSector` — deployment posture flag
6. `hasActiveProfile` — profileStore has active selection
7. `needsHumanDecision` — aggregator: any blocking signal true
8. `remoteRunnerActive` — any healthy/online runner

**5 counts** (auxiliary numeric signals): activeRuns / pendingApprovals / openReviewSessions / remoteRunnerCount / evidenceLedgerEntries

**7 adapters** (per-adapter try/catch, sources.<id>.errored on throw): approvalManager / reviewSessionManager / runRegistry / deploymentProfile / evidenceLedger / profileStore / remoteRunner

**needsHumanDecision aggregator semantics**:
- approvalPending OR codexReviewMissing → true
- (publicSector && hasPii) → true (matches GOV-PII-0 escalation)
- !hasActiveProfile → true (fail-safe; absent profileStore = unknown setup)
- Standard mode + PII alone → false (warning, not blocker)

### 1.2 SMART-0-b — HTTP route (commit `b1c1bf4`)

| File | Role |
|---|---|
| `src/routes/decisionContextRoutes.js` | `GET /api/decision-context` |
| `server.js` (modified) | Mount + 7 adapter wiring |
| `tests/integration/decision-context.test.js` | 9 integration tests |

**Route contract**:
- `GET /api/decision-context` → 200 JSON snapshot
- `x-harness-has-pii: 1` header → hasPii flag set true
- Adapter shim layer normalizes server-side method names:
  - `runRegistry.list()` preferred; `.listAll()` fallback
  - `runnerRegistry.snapshot()` preferred; `.list()` fallback
  - `evidenceLedger.count()` preferred; `.size()` fallback
- Read-only — no token gate (loopback binding is the safeguard)
- Single throwing adapter → still 200 + sources.<id>.errored captured (NOT a 500)

`server.js` mount uses existing singletons:
```js
app.use("/api", createDecisionContextRoutes({
  approvalManager: _approvalManager,
  reviewSessionManager: _reviewSessionManager,
  runRegistry: pipelineOrchestrator,
  deploymentProfile: _deploymentProfile,
  evidenceLedger,
  profileStore,
  runnerRegistry: _remoteRunner.runnerRegistry,
}));
```

## 5. Known limitations + follow-ups

### 5.1 SMART-0 round itself
- `hasPii` is opt-input via header — operator-side panel must call /api/decision-context with the header, OR a piiScanner-aware route variant could surface the flag automatically. Current design preserves piiScanner statelessness.
- 5s polling interval (default) is fine for steady state; new state changes (e.g., approval just arrived) wait up to 5s to surface. Future: WebSocket push could collapse latency to ~0s, but at design-complexity cost.
- No client-side adapter parallel — buildContext lives only server-side. Browser-only state (e.g., last operator click time) isn't part of decisionContext. Future SMART rounds can extend if needed.
- `needsHumanDecision` aggregator is hardcoded — SMART-2 Policy Packs may want pluggable aggregator logic per posture.

### 5.2 Out-of-scope (later SMART rounds)
- **SMART-1 Recommendation Cards** — first consumer of decisionContext. Reads booleans → renders prioritized recommendation cards in simple shell.
- **SMART-2 Policy-backed Hard Gates** — uses booleans + posture to enforce deny on dispatch (cap movement candidate).
- **SMART-3 Expert Review Presets** — uses context flags to pre-fill review prompts.
- **SMART-4 Redacted Run Memory** — sources `decisionContext` snapshot at decision time for "what was happening when this approval fired".
- **SMART-5 Institutional Policy Packs** — pluggable rules consume same adapter outputs (cap movement candidate).
- **SKILL-PACK-0** — distributable expertise consuming decisionContext for skill activation.
